- #TODO-0004 Move the work queue out of process memory into separate storage (e.g. Redis or a SQLite file on a mounted volume), so a container restart doesn't lose pending/in-flight requests. Today there is no explicit queue: updates are handled in-process by aiogram polling ([UFB-0020](features/UFB-0020-in-process-bot-polling.md)) and downloads run inline, so a restart drops whatever is mid-download; decide the queue shape first, then the store, and what a restarted worker should resume or re-reply.
- #TODO-0005 Split the single process into separate components — a receiver (gets updates from Telegram), a downloader, and a messenger (sends replies back to Telegram) — so each can be scaled and run in parallel. Today all three run in one process ([UFB-0020](features/UFB-0020-in-process-bot-polling.md)) and downloads block inline; needs a hand-off between components, which pairs with #TODO-0004 (queue in separate storage). Decide the component boundaries and the shared cache/volume access first.

- #TODO-0008 Profile links — when a link points at a user profile (Instagram, TikTok, Twitter/X, Reddit, YouTube channel, etc.) instead of a post, reply with a profile card rendered as an Instant View page ([UFB-0032](features/UFB-0032-telegram-instant-view-embeds.md)): username, display name, avatar, bio/description, follower counts where available. Today profile links get no useful treatment (Instagram is only matched on `/p/` and `/reel/`, see [UFB-0011](features/UFB-0011-platform-mirror-rewrites.md)). Needs a per-platform way to fetch profile metadata (yt-dlp can often extract channel/user info, otherwise a scraper or the platform's mirror service); decide the template (a new `profile.html` beside `watch.html`, [UFB-0033](features/UFB-0033-static-page-generation.md)) and how the avatar is cached ([UFB-0016](features/UFB-0016-download-caching.md)). Shares the metadata-extraction groundwork with #TODO-0002.
- #TODO-0009 Song identification alongside the downloader — name the music playing in a downloaded video and add title/artist (plus a link) to the reply and watch page. Start cheap: read `track`/`artist` from yt-dlp's info dict where the platform provides them (e.g. TikTok), which needs no recognition. For the rest, extract 10–20 s of mono audio from the cached file with ffmpeg (as `app/media.py` already does for loudness) and run a recognizer off the event loop: `shazamio` is the easiest (async, unofficial, can break and sits in a terms-of-service gray area); ACRCloud or AudD are stable commercial APIs with free tiers; AcoustID/Chromaprint is open but weak on music under speech. Dejavu/audfprint/Olaf only match a self-built database, so they don't fit. Make it opt-in via a setting and prefer on-demand (a button on the reply or a `/song` command) over running on every download, since it adds seconds of latency and an external dependency. Cache the result in the metadata store from #TODO-0002 so repeat requests don't pay for recognition again.

- #TODO-0011 Duplicate detection — when the same link was already processed in this chat recently, reply by linking the earlier reply (or re-sending the cached file) instead of repeating the download and a second full reply. The download cache already avoids re-downloading ([UFB-0016](features/UFB-0016-download-caching.md)); what's missing is remembering, per chat, which message answered which URL and for how long, so it needs a small persistent store (shares groundwork with #TODO-0002). Decide the window and whether it applies in group chats, where [UFB-0004](features/UFB-0004-group-chat-quietness.md) quietness already limits replies.

- #TODO-0013 Cobalt as a fallback downloader — when `yt-dlp` fails, try a self-hosted [cobalt](https://github.com/imputnet/cobalt) API before falling back to the mirror link ([UFB-0013](features/UFB-0013-download-failure-fallback.md)). cobalt and yt-dlp break at different times, so it catches some failures the other misses. Plan: an optional `cobalt` service in `docker-compose.yml` behind a profile (like `telegram-bot-api`), a `COBALT_API_URL` setting that leaves everything unchanged when empty, and the result saved under the same cache stem ([UFB-0016](features/UFB-0016-download-caching.md)). Run it as a separate container and call its HTTP API only, so its AGPL license doesn't reach the bot; don't rely on the public `cobalt.tools` instance (rate-limited, needs auth). It returns little metadata, so it doesn't help #TODO-0002. Record which downloader succeeded in the metrics (#TODO-0006) to judge whether it earns its keep. Supersedes the evaluation in #BUG-0035.
- #TODO-0014 Multiple cookie jars — support several cookie sets per site (e.g. more than one account) instead of merging every `cookies*.txt` into a single jar ([UFB-0017](features/UFB-0017-cookie-file-merging.md), [UFB-0018](features/UFB-0018-persistent-cookie-jar.md)). Pick a jar per request and move to the next one when a download hits a login wall or a rate limit, so one burned or throttled account doesn't fail every request for that platform. The keepalive ([UFB-0038](features/UFB-0038-cookie-keepalive.md)) would then track health per jar and take a dead one out of rotation. Decide how jars are named and mapped to sites (file-name convention or a small config), whether rotation is round-robin or on-failure only, and how `/health` reports per-jar state.
